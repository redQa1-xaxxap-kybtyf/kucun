# 幂等性实现问题分析与解决方案

## 问题根本原因

### 1. 数据溢出原因

- TEXT字段限制: 64KB
- 入库响应数据包含: 嵌套的product对象、user对象、扁平化字段
- 当productName、userName、remarks等字段内容较多时,JSON序列化后可能超过64KB

### 2. 错误的优化方案

之前实现的`extractKeyRequestData()`函数存在严重问题:

- ❌ 违背幂等性最佳实践(应存储完整请求数据)
- ❌ 丢失审计信息(inputQuantity, inputUnit等用户输入)
- ❌ 无法准确重现请求(调试困难)

## 行业最佳实践 (Stripe/Shopify)

### 核心原则

1. **完整存储**: 存储完整的请求和响应数据
2. **独立表**: 幂等性表与业务数据表分离
3. **有限期**: 24-72小时后过期清理
4. **原子性**: 在同一事务中存储幂等性记录和执行业务逻辑

### 数据存储策略

- `requestData`: 完整的原始请求数据(用于审计)
- `responseData`: 完整的响应数据(用于返回相同结果)
- 无论成功失败都存储

## 正确的解决方案

### 方案1: 使用MEDIUMTEXT (当前方案)

- ✅ 简单直接,扩展存储容量到16MB
- ✅ 保留完整数据,符合最佳实践
- ⚠️ 对于极大数据量仍有风险

### 方案2: 优化响应数据存储

不修改请求数据存储(保持完整),但优化响应数据:

```typescript
// 只存储核心响应信息,不存储冗余的嵌套对象
const minimalResponse = {
  id: record.id,
  recordNumber: record.recordNumber,
  success: true,
};
```

### 方案3: 引入Redis (长期方案)

- 使用Redis存储幂等性记录
- 更快的查询性能
- 自动过期机制
- 减少数据库负担

## 建议实施步骤

1. **立即**: 撤销extractKeyRequestData优化,恢复完整数据存储
2. **短期**: 保持MEDIUMTEXT方案,监控数据大小
3. **中期**: 评估是否需要引入Redis
4. **持续**: 实现自动清理过期记录的定时任务
