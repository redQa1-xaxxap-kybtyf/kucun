# 库存管理系统打包发布指南

本文档说明如何在本地生成宝塔部署用的打包文件，并区分「首次部署」和「版本升级」的操作方式，避免每次临时摸索、误删代码或把部署产物提交到 Git。

## 1. 适用范围与目录约定

- 项目根目录：`E:\kucun`
- 部署工作目录：`bushu/kucun-baota-deployment/`
  - 存放要上传到服务器的完整应用目录（代码 + 配置模板 + 部署脚本）。
- 部署压缩包：`bushu/kucun-baota-deployment-vX.Y.Z.zip`
  - 每次打包生成一个新的 zip 文件，例如：`kucun-baota-deployment-v1.0.9.zip`。
- Git 忽略规则：
  - `.gitignore` 已忽略 `bushu/`、`deployment-package/`、`deployment-output/` 等目录。
  - 部署包相关文件不会进入 Git，保证工作区保持干净。

## 2. 打包前准备

1. 在项目根目录确认 Git 状态：

   ```bash
   git status -sb
   ```

   确认没有意外改动（或只包含你本次要发布的改动）。

2. 可选：本地自测关键功能（仪表盘、库存、销售、财务、个人中心、登录流程等）。

## 3. 标准打包流程（本地）

> 下面所有命令都在项目根目录 `E:\kucun` 执行。

### 3.1 构建最新前端与 API

```bash
npm run build
```

此命令会生成最新的 `.next/` 目录。宝塔服务器上不再执行 `next build`，而是直接使用本地构建好的 `.next`。

### 3.2 清理旧的部署代码（仅 bushu 目录）

删除旧的应用代码目录（注意：**只删除 bushu 里的对应目录**）：

- `bushu/kucun-baota-deployment/.next/`
- `bushu/kucun-baota-deployment/app/`
- `bushu/kucun-baota-deployment/components/`
- `bushu/kucun-baota-deployment/hooks/`
- `bushu/kucun-baota-deployment/lib/`
- `bushu/kucun-baota-deployment/prisma/`
- `bushu/kucun-baota-deployment/public/`

不要删除以下内容：

- `bushu/kucun-baota-deployment/deployment-scripts/`
- `bushu/kucun-baota-deployment/docs/`
- `bushu/kucun-baota-deployment/logs/`
- `bushu/kucun-baota-deployment/.env.production.template`
- `bushu/kucun-baota-deployment/ecosystem.config.js`
- `bushu/kucun-baota-deployment/README.md`

### 3.3 拷贝最新代码与配置到部署目录

从项目根目录复制以下目录到部署目录：

- `app/`
- `components/`
- `hooks/`
- `lib/`
- `prisma/`
- `public/`
- `.next/`

复制以下配置文件覆盖部署目录中的同名文件：

- `middleware.ts`
- `instrumentation.ts`
- `next.config.ts`
- `tsconfig.json`
- `package.json`
- `package-lock.json`
- `components.json`

注意：**不要**把 `.env`、`.env.local`、`.env.production` 等真实环境变量文件拷贝到部署目录，只保留模板文件 `.env.production.template`。

### 3.4 更新版本号（应用 & 部署包）【必做】

> 系统左下角/右上角显示的「系统版本」来自运行时的 `npm_package_version` 环境变量，
> 实际就是 **服务器上应用目录里的 `package.json` 的 `"version"` 字段**。
> 只有把版本号更新到部署目录，线上界面才会看到版本变化。

> **规则：只要要发版、要给生产环境用的新包，就必须升级版本号。**
> 也就是说：同一个版本号只能对应一份构建结果，不能拿旧版本号反复打包上线。

打包前，请按以下顺序统一更新版本号，保持「代码 / 部署目录 / 压缩包」三者一致：

1. 应用版本（项目根目录 package.json）

   编辑项目根目录的 `package.json`（示例）：

   ```json
   {
     "name": "kucun",
     "version": "1.0.10",
     ...
   }
   ```

   这个版本号会：
   - 通过 Node 的 `npm_package_version` 暴露给应用（`/api/settings/basic` → `systemVersion`）。
   - 出现在健康检查接口、日志和系统界面中，用于标识当前运行的应用版本。

2. 同步版本号到部署目录 package.json（**关键步骤，决定线上实际版本**）

   根目录版本号改好之后，需要 **覆盖部署目录里的 `package.json` 和 `package-lock.json`**：

   ```powershell
   # 在 E:\kucun 下执行
   Copy-Item package.json, package-lock.json bushu\kucun-baota-deployment\ -Force
   ```

   覆盖完成后，确认 `bushu/kucun-baota-deployment/package.json` 中的 `"version"` 和根目录保持一致，例如：

   ```json
   {
     "name": "kucun",
     "version": "1.0.10",
     ...
   }
   ```

   以后部署到服务器时，宝塔解压的就是这一份目录，
   服务器 Node 进程看到的 `npm_package_version` 就是这里的 `"version"`。

3. 部署目录 README（bushu/kucun-baota-deployment/README.md）

   编辑 `bushu/kucun-baota-deployment/README.md`，更新：
   - `版本: X.Y.Z`
   - `生成时间: YYYY-MM-DD HH:mm:ss`

   例如：

   ```text
   版本: 1.0.10
   生成时间: 2025-12-04 08:11:40
   ```

   这个只是给人看的说明文档，方便你在宝塔里快速确认当前部署包的版本和生成时间。

4. 压缩包文件名

   打包时压缩包命名也要使用同一版本号，例如：
   - `kucun-baota-deployment-v1.0.10.zip`

> 建议：每次发布前先确定一个新版本号（例如 `1.0.10` → `1.0.11`），然后按顺序同步到：
> 1）根目录 `package.json`，2）部署目录 `bushu/kucun-baota-deployment/package.json`，
> 3）`bushu/README.md` 和 4）zip 文件名，保持四者一致。
> 版本号可以与 Git Tag 对齐，便于回溯线上版本对应的代码提交。

### 3.5 生成部署压缩包

在 PowerShell 中执行：

```powershell
Compress-Archive `
  -Path 'bushu\kucun-baota-deployment\*' `
  -DestinationPath 'bushu\kucun-baota-deployment-v1.0.9.zip' `
  -Force
```

命令完成后，`bushu/` 目录下应至少有：

- `kucun-baota-deployment/`（展开后的部署目录）
- `kucun-baota-deployment-v1.0.9.zip`（本次要上传的部署包）
- 可能还保留历史包，如 `kucun-baota-deployment-v1.0.8.zip`

### 3.6 再次确认 Git 状态

```bash
git status -sb
```

正常情况下应保持：

```text
## <当前分支名>
```

没有新增改动，说明打包操作只发生在 `.gitignore` 中的目录，不会污染版本库。

## 4. 服务器部署流程

以下步骤在宝塔服务器上执行，假设代码解压目录为 `/www/wwwroot/your-domain.com`。

### 4.1 首次部署（全新安装）

1. 将本地生成的 `kucun-baota-deployment-vX.Y.Z.zip` 上传至服务器目标目录。
2. 在服务器上解压：

   ```bash
   cd /www/wwwroot/your-domain.com
   unzip kucun-baota-deployment-vX.Y.Z.zip
   ```

3. 配置生产环境变量：

   ```bash
   cd /www/wwwroot/your-domain.com
   cp .env.production.template .env.production
   nano .env.production   # 或使用宝塔在线编辑，填入实际配置
   ```

4. 执行首次部署脚本（自动安装依赖、生成 Prisma Client、执行迁移）：

   ```bash
   cd /www/wwwroot/your-domain.com
   ./deployment-scripts/deploy-first-time.sh
   ```

5. 使用 PM2 启动应用（如部署文档中所示）：

   ```bash
   pm2 start ecosystem.config.js --env production
   pm2 save
   ```

6. 在宝塔中配置 Nginx 反向代理、SSL 等，直至站点可正常访问。

### 4.2 版本升级部署（已有旧版本）

升级时，部署包结构与首次部署 **完全一致**，区别只在于服务器使用的脚本不同。

1. 可选：备份当前目录或保留旧 zip 包。
2. 将新的 `kucun-baota-deployment-vX.Y.Z.zip` 上传到服务器原目录。
3. 在服务器上解压覆盖：

   ```bash
   cd /www/wwwroot/your-domain.com
   unzip -o kucun-baota-deployment-vX.Y.Z.zip
   ```

4. 执行更新脚本（依赖变更时会自动安装；然后生成 Prisma Client、执行迁移、重启 PM2）：

   ```bash
   cd /www/wwwroot/your-domain.com
   ./deployment-scripts/update-app.sh
   ```

5. 通过浏览器和 PM2 日志验证新版本是否正常运行。

## 5. 注意事项与建议

- **不要提交部署产物**：`bushu/`、`deployment-output/` 等目录已经在 `.gitignore` 中，保持现状即可，避免误提交。
- **始终本地构建 `.next`**：
  - 部署脚本设计为直接使用本地构建结果，不在服务器上执行 `next build`。
  - 每次打包前务必执行 `npm run build`。
- **依赖安装策略**：
  - 首次部署时，由 `deploy-first-time.sh` 执行 `npm ci` 安装完整依赖。
  - 后续版本升级时，`update-app.sh` **默认不在服务器安装依赖**（避免内存不足导致 `npm ci` 被 Killed）。
  - 如确需安装依赖（确认本次发布确实改了依赖），执行：
    - `INSTALL_DEPS=1 ./deployment-scripts/update-app.sh`
  - 当跳过依赖安装时，升级过程会直接生成 Prisma Client、执行迁移并重启 PM2。
- **环境变量与密钥保密**：
  - `.env.production` 只存在于服务器，不应出现在项目仓库或部署包中。
  - 只在部署包中保留 `.env.production.template` 作为填写示例。
- **版本号管理**：
  - 建议统一使用语义化版本号（例如 `1.0.9`）。
  - 可以与 Git Tag 对齐，便于回溯线上版本对应的代码提交。

按照本指南操作，你只需要记住两件事：

1. 本地打包：**固定流程** → 构建 → 同步代码到 `bushu/kucun-baota-deployment/` → 更新版本 → 压缩为 zip。
2. 服务器操作：**首次部署用 `deploy-first-time.sh`，升级版本用 `update-app.sh`**。

这样就可以稳定、重复地生成和发布新的部署包，而不会再影响本地开发环境和 Git 工作区。

## 6. 数据库结构变更规范（必须配套迁移）

> 这条是本项目里曾经出现过的严重疏忽：  
> **只改了 Prisma 模型，没有新增迁移，导致生产数据库少字段，线上接口 500。**
> 典型案例：`InventoryAdjustment.totalCost` 字段缺少 `total_cost` 列，月度报表直接报错。

今后统一按下面的规范执行：

1. **只要改 `prisma/schema.prisma`（新增字段 / 表 / 索引），就必须生成新的 Prisma 迁移**
   - 使用命令（开发环境）：
     ```bash
     npx prisma migrate dev --name <简短说明>
     ```
   - 确认生成了新的 `prisma/migrations/时间戳_描述/migration.sql`。

2. **禁止只改 schema 而不生成迁移就发版**
   - 否则生产库结构不会自动更新，即使 `update-app.sh` 里跑了 `prisma migrate deploy` 也无效。
   - 这会造成本地一切正常、生产环境 500 的典型“惊喜”。

3. **如确实需要紧急在生产库执行手工 SQL（热修复），必须同步写回仓库**
   - 将同样的 `ALTER TABLE ...` 语句写入新的 Prisma 迁移，或补充到 `migrations.sql` 中。
   - 确保之后新环境搭建 / 旧环境补齐时不会遗漏这个结构变更。

4. **发版前快速自检**
   - 确认：`prisma/migrations` 中是否存在最近一次结构改动对应的迁移目录；
   - 在本地执行一次：
     ```bash
     npx prisma migrate deploy --preview-feature
     ```
     确认不会报“没有要执行的迁移”和明显错误。

只要遵守这条规范，像“月度报表因为缺少 `total_cost` 列直接 500”这种严重事故，就可以在本地提前暴露并解决，而不会带到生产环境。\*\*\*
