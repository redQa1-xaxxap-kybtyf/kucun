# 项目产品经理评估报告（kucun 瓷砖行业库存管理系统）

**报告日期**：2025-12-25  
**评估范围**：Web ERP（Next.js 后台）+ 微信小程序端（kucunxcx）+ 数据/权限/运维能力  
**评估方法**：基于代码结构与项目文档的“桌面评估”（不包含真实用户访谈与生产数据分析）

---

## 1. 执行摘要（给管理层的 3 分钟版本）

### 1.1 产品定位与阶段判断

- **定位**：面向瓷砖行业的中小型商贸/仓储/门店的“进销存 + 财务核算 + 批次/色号”一体化系统，配套小程序用于移动端浏览/查询与轻量操作。
- **当前阶段**：功能面较完整、工程化基础良好，但**生产可用性与“新手可用性”仍是最大瓶颈**；更像“可用 Beta / 小范围试点”而非“可规模化推广”。

### 1.2 结论评分（PM视角）

| 维度 | 评分 | 结论 |
|---|---:|---|
| 业务流程完整度 | 8/10 | 覆盖核心流程，批次+色号能力突出 |
| 核算可信度（成本/利润） | 5/10 | 存在已知缺口，影响经营决策信任 |
| 新手可用性（学习成本） | 5/10 | 规则复杂、缺少引导与“安全操作替代” |
| 运营与交付能力（上线/回滚/排障） | 7/10 | 有脚本/文档，但对小白不友好 |
| 工程可维护性（迭代效率） | 6/10 | 架构好但类型错误/超长文件拖慢迭代 |

### 1.3 最重要的三件事（建议按顺序做）

1. **把“不能删/不能改/权限不足”这类规则，产品化为“可理解、可替代、可完成任务”的流程**（例如：停用/归档、清零库存引导、原因解释、下一步按钮）。
2. **补齐成本/费用分摊与利润公式的“可解释核算闭环”**（尤其销售订单成本与费用分摊，直接影响管理层信任与复购）。
3. **消灭阻塞上线的工程红线（TypeScript 错误、超长文件、关键路径测试）**，否则每次“生产救火”都会反复发生。

## 2. 产品与用户画像

### 2.1 典型用户角色（建议产品内显式化）

- **老板/经营者**：关注利润、毛利、欠款、周转；期望“看报表就能做决策”。
- **销售**：快速开单、查库存、查价格、客户往来；最怕“信息找不到/操作慢/出错要返工”。
- **仓管/库管**：入库、出库、盘点、批次、色号；最怕“批次乱/单位换算错/库存不准背锅”。
- **财务**：收付款、对账、费用归集与分摊；最怕“口径不一致/数据不可追溯”。
- **外部客户/游客（小程序）**：看货、看图、看库存/状态；不一定懂 ERP 术语，最怕“看不懂/看不到/没有下一步”。

### 2.2 核心价值主张（建议对外一句话）

> 用“批次 + 色号 + 件片数换算”的行业模型，把库存、订单、发货、费用与核算串成一条线；让门店/仓库/财务在同一套口径里协作。

## 3. 功能盘点与产品结构评价

### 3.1 Web ERP（后台）能力概览

- **产品/分类/变体（色号）**：基础信息 + 状态管理；具备行业适配的变体维度。
- **库存**：批次 + 变体维度管理，且有盘点/调整等完整流程基础。
- **销售/退货/厂家发货/采购/应收应付/付款收款**：覆盖面广，具备业务闭环雏形。
- **运输查询与安全/缓存/监控**：存在较完整的工程化文档与策略，说明团队有“系统化交付能力”。

### 3.2 小程序端能力概览

- **产品浏览链路（首页/列表/详情）**：视觉与信息层级较好，已具备搜索/筛选/布局切换等效率能力，整体“看货找货”的体验基础扎实。
- **权限差异（游客 vs 登录）**：存在“看不到原因不解释”的体验断点，用户容易误解为“系统没数据/数据不透明”，造成流失与信任损耗。
- **创建/编辑产品（策略风险点）**：需要明确小程序的目标用户与边界：  
  - 若**面向外部客户/游客**：建议更偏“浏览/收藏/询价/下单/联系”链路，减少高风险写操作入口。  
  - 若**面向内部移动办公**：可以保留创建/编辑，但必须配套“防错 + 引导 + 可回退”，并强化权限与审计（否则会频繁出现误操作与数据治理成本）。

## 4. 体验评估（PM视角：能否让小白完成任务）

### 4.1 当前最典型的“新手坑”

1. **删除/修改被业务规则阻止**  
   - 用户心智：我创建错了，所以我想删。  
   - 系统现实：一旦产生库存/入库/销售记录就不能删（合理）。  
   - 问题：缺少“为什么不能删 + 我下一步该怎么做”的产品化承接。

2. **权限差异不可见**  
   - 访客看不到库存数字，但若不解释，会被理解为“系统没数据/坏了/不透明”。

3. **复杂对象的生命周期缺少“状态机”表达**  
   - 例如产品、变体、批次、订单、入库记录等，应当在 UI 上明确“可做什么/不可做什么/下一步是什么”。

### 4.2 解决思路：把“规则”改造成“流程”

建议在关键对象上统一落地以下产品化能力（Web + 小程序一致）：

- **对象生命周期**：`草稿 Draft` → `启用 Active` → `停用 Inactive` →（可选）`归档 Archived`  
  - 现阶段若不支持 Draft/Archived，也建议至少把 **Active/Inactive** 产品化（“不用了=停用”，而不是“删不掉=卡死”）。
- **阻止型操作的“替代路径”**（把“不能做”改成“下一步能做什么”）：  
  - 删除失败 → 弹窗给出原因，并提供 **一键停用（推荐）** + “查看关联记录/去处理库存”的入口  
  - 需要清零库存 → 引导到“库存调整/盘点差异处理”，并给出安全提示（高权限、会留痕）  
  - 需要撤销入库 → 引导到“反向入库/冲销记录/出库回滚”（保留审计与追溯）
- **解释机制**：统一错误提示模板 = **原因 + 影响 + 推荐操作 + 联系谁**  
  - 示例：`无法删除：该产品已产生入库/库存记录，为保证账务一致性不允许删除。建议：停用产品（推荐） / 去清零库存 / 查看关联记录。`

## 5. 业务规则与数据一致性（信任建设）

### 5.1 删除限制是对的，但需要“可理解”

“有库存/入库/销售记录不可删除”是 ERP 的正确方向：保证审计与对账不被破坏。  
PM 的关键是把这件事变成用户能理解且能继续完成工作的体验：

- UI 文案：明确“为了账务一致性，不能删除”  
- UI 动作：给“停用（推荐）”“去清零库存”“查看关联记录”  
- 权限：清零/冲销应是高权限，并带操作日志

### 5.2 核算闭环的产品风险

项目文档中已明确指出：**销售订单成本、费用分摊、利润公式存在缺口/口径风险**。  
这会直接带来两个后果：

1. 老板不信报表 → 系统价值打折 → “只当记账/记库存用”
2. 财务与业务扯皮 → 反而增加沟通成本

建议把“核算口径”当作一等公民：

- **统一利润公式与口径**：明确并固化为系统标准（例如：`利润 = 收入 - 成本 - 费用`），并在报表/详情页给出解释入口（“口径说明”）。
- **可解释的计算路径**（让财务/业务对齐同一套叙事）：  
  - 成本从哪里来（库存加权平均/FIFO/人工录入的优先级与回溯规则）  
  - 费用怎么分摊（按货值/按重量/按数量/按归属等策略，以及误差如何兜底）  
  - 哪些情况属于估算（例如缺失成本、历史批次缺字段）以及如何修正
- **报表的“风险标注”机制**：在关键指标旁用标签/提示明确：`未计入运费`、`成本估算`、`缺少批次成本` 等，避免误导经营决策。

### 5.3 销售与财务“计算偏差”核查结论（基于代码审计）

以下结论聚焦“同一指标在不同链路/不同页面计算口径不一致”带来的偏差风险（会直接影响应收、毛利/利润与经营报表可信度）：

1. **应收口径：`totalAmount` 是否包含 `roundingAdjustment` 存在不一致**
   - 多处财务/应收计算假设：`实际应收 = totalAmount + roundingAdjustment`（例如：`lib/api/handlers/sales-orders/detail.ts`、`lib/services/receivables-helpers.ts`、`app/(dashboard)/finance/payments/page.tsx`）。
   - **已落地修复（2025-12-25）**：统一保持 `totalAmount` 不含抹零；所有应收/结清判断统一使用 `实际应收 = totalAmount + roundingAdjustment`。
   - **影响**：抹零为负（优惠）时可能提前显示“已结清”；抹零为正（加价）时可能长期显示“仍欠款”。

2. **销售草稿更新 vs 创建：成本/利润计算口径不一致**
   - 创建链路使用统一财务计算与费用分摊（`lib/api/handlers/sales-orders/financials.ts`），会把公司承担费用分摊到行并影响 `costAmount/profitAmount`。
   - 草稿更新链路一度只按“售价 - 成本”计算调货毛利，未把公司承担费用纳入成本/利润，且行级分摊缺失（`lib/api/handlers/sales-orders/update-draft.ts`）。
   - **影响**：同一订单在“创建后 vs 草稿编辑后”可能出现毛利/利润跳变，引发财务与业务对账争议。

3. **“公司承担费用”可能在经营报表中被重复扣减（双重计入）**
   - 系统可自动把公司承担费用落到 `ExpenseRecord`（`lib/services/expense-service.ts`，且 `EXPENSE_AUTO_CREATE` 默认开启于 `lib/env.ts`）。
   - 同时，销售订单链路又可能把公司费用分摊进订单成本字段（`costAmount/costSubtotal`）。
   - 而利润表/月报/年报会同时汇总 `salesOrder.costAmount`（成本）与 `expenseRecord`（费用）（例如：`lib/services/profit-loss-service.ts`、`lib/services/monthly-report-service.ts`、`lib/services/annual-report-service.ts`）。
   - **影响**：净利润被系统性低估（同一笔公司费用既进“成本”又进“费用”）。实践上应明确“费用进成本 or 进费用”的唯一口径，并在报表侧做过滤兜底，避免重复扣减。

4. **调货“混合模式（MIXED）”存在结构性偏差风险（销售额与成本基数不匹配）**
   - 多处实现对 MIXED 的处理是“销售额按整行 subtotal 计入，但成本只按 transferQuantity 计算”，会放大毛利/利润（见 `lib/api/handlers/sales-orders/financials.ts` 与 `lib/api/handlers/sales-orders/update-draft.ts` 的成本口径）。
   - 订单详情页又额外按 `transferQuantity/quantity` 对销售额做比例拆分显示“调货毛利”（`app/(dashboard)/sales-orders/[id]/page.tsx`），与订单表落库字段口径不完全一致。
   - **影响**：MIXED 订单在报表/详情/导出之间出现“看起来都对，但数字对不上”的典型口径冲突。

5. **费用合计口径风险：`additionalFees` 需要严格区分 paidBy**
    - 若把所有 feeItems 都加到 `additionalFees`，会把“公司承担费用”错误计入应收，导致订单总额虚高、应收虚高（见 `lib/services/sales-order-management/ExpenseManagementService.ts` 的重算逻辑风险点）。

6. **预收款（Prepayment）冲抵未纳入“订单已付/未付/自动完结”**
   - 订单 paid/remaining 的计算曾只统计“已确认收款”，忽略 `PrepaymentUsage`（预收款冲抵），导致：使用预收款的订单长期显示“仍欠款/无法完结”。
   - **已落地修复（2025-12-25）**：订单已付/未付与“发货后自动完结”统一把 `confirmed paymentAmount + prepaymentUsages.sum(appliedAmount)` 纳入口径。

7. **收款确认与往来账副作用存在绕过路径**
   - 收款确认链路若允许通过通用更新接口直接改 `status`，会绕过“往来账写入/订单 paidAmount 回写/自动完结”等关键副作用。
   - **已落地修复（2025-12-25）**：禁止通过 `PUT /api/payments/[id]` 修改状态与关键字段；确认必须走专用确认接口，并在确认前强校验 `paymentAmount = actualPaymentAmount + roundingAmount`，避免抹零口径叠加。

结论：当前销售与财务模块确实存在可导致“应收/利润/报表”偏差的口径不一致点。建议将“字段含义（口径）”写入产品说明与代码层统一函数，并建立 3-5 个典型订单（普通/调货/混合/含费用/含抹零）的自动化回归用例，确保创建、编辑、发货、收款、报表五条链路结果一致。

### 5.4 销售模式全景（口径 + 流程 + 风险）

本项目的“销售”至少包含以下模式（以销售订单为核心，按履约与核算差异拆解）。每个模式都需要一套**可落库、可重算、可解释**的口径合同，否则就会出现“页面能看、数字对不上、对账扯皮”的典型失败。

| 模式 | 定义 | 库存动作 | 成本来源 | 关键字段口径 | 主要风险点 |
|---|---|---|---|---|---|
| **A. 普通销售（NORMAL）** | 本地仓发货为主 | 确认时预留；发货时 FIFO/单位成本扣减并落出库 | 发货阶段以 FIFO 实耗为准（草稿阶段只能估算） | `totalAmount` 不含抹零；`实际应收 = totalAmount + roundingAdjustment` | 草稿/确认阶段利润只能“估算”；缺失成本需显式标注 |
| **B. 客户直发/纯调货（TRANSFER + SUPPLIER_ONLY）** | 供应商直发给客户 | 不预留/不扣减本地库存 | 以 `unitCost`（供应商成本）为主，可在确认时即稳定 | `transferQuantity = quantity`；利润应可直接解释 | 自动生成采购单/应付与销售成本口径不一致会导致供应链对账断裂 |
| **C. 混合履约（TRANSFER + MIXED）** | 同一订单既有本地发货也有调货直发 | 本地部分需要预留+发货扣减；调货部分不扣本地 | 本地部分=FIFO；调货部分=`unitCost * transferQuantity` | `localQuantity + transferQuantity = quantity`；成本需拆分再汇总 | **结构性偏差高发**：销售额按全量、成本只按调货或只按本地都会把利润算“虚高/虚低” |
| **D. 手动产品（isManualProduct）** | 订单里存在无库存产品ID的行 | 不应触发库存动作 | 需要明确“成本从哪来”：录入/估算/后补 | 必须能追溯其成本与费用分摊 | 若允许在 NORMAL 中出现，会造成“发货不扣库存但计入收入”的审计风险 |
| **E. 费用归属（feeItems paidBy）** | 客户承担 vs 公司承担 | 不影响库存，但影响利润与报表 | 公司承担费用需要分摊到订单/明细并可追溯 | `additionalFees=客户承担费用`；`expenseAmount=公司承担费用` | 若把公司费用算进应收或在报表里重复扣减，会系统性扭曲利润 |
| **F. 抹零与收款差额** | 下单抹零 vs 收款差额 | 不影响库存 | 影响应收与收入归集 | `roundingAdjustment`（订单抹零）≠ `paymentRounding`（收款差额） | 把抹零写进 `totalAmount` 会导致应收重复计算；把待确认收款抵扣应收会导致“提前结清” |
| **G. 退货/退款联动** | 退货单、退款单与销售单关联 | 退货应回补库存（或做损耗），并影响损益 | 退款影响净利润；退货影响收入/成本的回转口径 | 需要明确“退款 vs 退货”的口径边界 | 退货成本回转缺失会导致毛利/库存两边都不准 |
| **H. 厂家直发（FactoryShipmentOrder）** | 独立于销售订单的直发业务单据 | 不走本地库存（通常） | 采购成本 + 分摊费用，按应收金额核算利润 | `receivableAmount` 为应收口径主字段 | 与销售订单报表合并时易发生“费用重复扣减/利润重复合并”，必须定义合并规则 |

### 5.5 可执行落地计划（默认按 P0→P2 推进）

目标：把“销售所有模式”从“能用”升级到“可对账、可解释、可审计”，并保证报表/订单/收款三处数字一致。

**P0（1-3天，先止血，必须做）**
1. **写清字段合同并固化为代码共识**：明确 `totalAmount`/`roundingAdjustment`/`additionalFees`/`expenseAmount`/`costAmount`/`profitAmount` 的含义与公式（并在详情页提供口径说明入口）。
2. **统一应收口径**：全链路采用 `实际应收 = totalAmount + roundingAdjustment`；收款只用“已确认”抵扣应收，待确认只影响状态。
3. **打通客户直发的采购联动**：TRANSFER+SUPPLIER_ONLY 确认时能稳定生成采购单/应付，并确保成本口径一致（用计算后的成本，不依赖前端传入）。

**P1（4-10天，核心价值，决定“数据可信”）**
4. **把 MIXED 当作独立产品形态处理**：明确本地/调货两段的库存动作与成本来源；发货时本地段必须扣减库存并落出库记录；调货段不扣库存但要能对齐采购/供应商成本。
5. **补齐“估算 vs 实际”的可解释闭环**：草稿/确认展示估算成本与风险标签；发货回写实际成本并可一键重算；缺失成本必须标注原因与修正路径。
6. **费用分摊策略标准化**：默认按成本或货值分摊（与系统现有策略保持一致），明确兜底规则（最后一项差额兜底、全 0 时的回退逻辑），并确保订单头与订单行口径一致。

**P2（11-20天，质量保障，避免回归）**
7. **建立“销售模式回归样例库”（自动化）**：至少覆盖 6 个样例：NORMAL、TRANSFER_SUPPLIER_ONLY、TRANSFER_MIXED（含本地/调货拆分）、含公司费用、含抹零、含退货/退款；验收标准是“创建/编辑/发货/收款/报表五条链路一致”。
8. **UI/权限补齐审计体验**：关键指标旁标注 `估算成本/缺失成本/未计入某费用`；高风险操作（改价/改成本/重算）必须留操作日志与权限控制。

## 7. 优先级路线图（建议 30/60/90 天）

### 7.1 30 天：让“小白也能用”

- 产品对象：全面落地“停用/启用/归档”的交互与规则提示（Web + 小程序一致）
- 关键阻断点：删除失败、权限不足、看不到库存数字、创建后下一步不清晰
- 新手引导：首登引导 + 场景入口（我要开单/我要入库/我要盘点/我要看报表）

### 7.2 60 天：让“数据可信”

- 销售订单成本与费用分摊闭环（对齐厂家发货的成熟做法）：
  - **统一费用口径**：客户承担费用进入“应收”（`additionalFees`），公司承担费用进入“成本/费用”（`expenseAmount`），利润统一按 `收入-成本-费用`。
  - **统一分摊策略**：默认按货值分摊（与厂家发货一致），并支持按重量/按数量等策略（无重量数据时自动回退到按货值）。
  - **成本来源分层**：下单/草稿阶段展示“估算成本”（加权平均/FIFO预估/库存单位成本），发货/出库阶段回写“实际成本”（FIFO 实耗），并在界面明确标识估算 vs 实际，避免财务口径争议。
  - **可重算与可追溯**：费用项变化、订单项变化、状态变化触发自动重算；提供“重算成本/利润”按钮与操作日志（谁在什么时候以什么口径重算）。
  - **数据落库闭环**：订单行写入 `allocatedExpense/costSubtotal/profitAmount/profitMargin`，订单头写入 `expenseAmount/costAmount/profitAmount`，并保证报表读取同一套字段与同一套口径。
  - **验收标准（DoD）**：任一销售订单在“草稿/已确认/已发货”三种状态下，都能看到一致口径的成本/费用/利润；报表与订单详情一致；缺失成本时明确标注“估算/缺失原因”，且可一键触发重算。
- 运费/费用入成本口径统一，利润/利润率可解释
- 报表对“口径缺失”显式提示，避免误导经营决策

### 7.3 90 天：让“可规模化推广”

- 权限体系与审计日志：关键操作可追溯（停用/清零/冲销/价格修改等）
- 性能与稳定性：列表 P95、关键接口错误率、缓存策略统一
- 运营工具：内置帮助中心/FAQ、可导出诊断包（给客服/实施用）

## 8. 建议的关键指标（上线后必须看）

### 8.1 业务指标（PM核心）

- 首周激活率（完成 3 个关键任务的用户占比）
- 关键任务成功率：入库、出库、开单、收款、盘点

- 经营者留存：每周查看报表次数

### 8.2 产品质量指标（对体验负责）

- “被规则阻止”事件数（删除失败、权限不足、库存不足…）
- “被阻止后仍能完成任务”的转化率（是否点了推荐替代操作）
- P95 接口耗时与前端页面可交互时间
- 关键错误率（500/空响应/请求失败）

## 9. 结语：产品策略建议

这个项目最强的资产是“行业模型 + 流程覆盖面 + 工程化意识”。  
下一阶段的产品成功关键不在于再加更多功能，而在于：

1) 把复杂业务规则用“解释 + 替代路径”包装成小白可完成的流程；  
2) 把成本/利润口径补齐，让系统成为“可信的经营仪表盘”；  
3) 用工程红线确保每次上线都可控，避免生产环境反复救火。
