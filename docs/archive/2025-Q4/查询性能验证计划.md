## 3. 验证方法

### 3.1 慢查询日志分析

已有的慢查询监控（`lib/db.ts:105-125`）会记录超过阈值的查询：

```typescript
// 当前配置
// 开发环境：500ms
// 生产环境：1000ms（可通过 PRISMA_SLOW_QUERY_THRESHOLD_MS 调整）
```

**验证步骤**：
1. 设置 `PRISMA_SLOW_QUERY_THRESHOLD_MS=100` 捕获更多查询
2. 运行典型业务操作流程
3. 收集慢查询日志，识别高频慢查询

### 3.2 EXPLAIN 执行计划分析

对每个 P0/P1 接口的核心查询执行 EXPLAIN 分析：

```sql
-- 示例：库存列表查询
EXPLAIN SELECT * FROM Inventory
WHERE productId = ? AND status = ?
ORDER BY createdAt DESC
LIMIT 20;

-- 检查点：
-- 1. type 应为 ref/eq_ref/range，避免 ALL
-- 2. key 应显示使用的索引名
-- 3. rows 应尽可能小
-- 4. Extra 避免 Using filesort / Using temporary
```

### 3.3 压力测试脚本

创建性能测试脚本验证实际负载下的表现：

```bash
# 使用 autocannon 或 k6 进行压测
npx autocannon -c 10 -d 30 http://localhost:3000/api/inventory

# 预期输出：
# - 平均响应时间
# - P50/P75/P95/P99 分位数
# - 错误率
```

## 8. 风险和注意事项

1. **测试环境数据量**: 确保测试数据量与生产环境相近
2. **并发模式**: 测试应模拟真实并发模式
3. **缓存影响**: 首次查询可能比后续查询慢（冷启动）
4. **网络延迟**: 本地测试与生产环境网络延迟差异
