# 小程序端新建销售订单功能开发评估（针对《小程序新建订单功能开发文档.md》）

评估日期：2025-12-17  
评估范围：开发文档的可落地性（接口契约、数据一致性、关键风险、验收标准），并对照当前仓库后端/小程序实现现状核验。  
结论摘要：文档结构完整（API/类型/服务/页面/计划齐全），但存在若干 **P0 级“接口与业务规则不一致”** 的问题，不修正会导致实现后无法联调或上线后高频失败。

---

## 1. 评估结论（按严重级别）

### P0：必须修正，否则无法稳定开发/联调

1. **订单号生成接口不存在**
   - 文档设计：`GET /api/sales-orders/generate-order-number`，并在创建页 `onLoad` 调用生成订单号。
   - 现状核验：仓库未实现该路由；后端在创建订单时直接生成订单号（`generateSalesOrderNumber()`）。
   - 建议：
     - 方案 A（推荐）：小程序不再“预先请求订单号”，创建成功后展示 `order.orderNumber`。
     - 方案 B：确实需要“提交前显示订单号”，则新增后端路由并明确权限与限流策略。

2. **客户搜索接口与参数不一致**
   - 文档设计：`/customers` + `search=关键词`，并假设返回 `data.items`。
   - 现状核验：轻量搜索接口是 `GET /api/customers/search?q=关键词&limit=...`，返回 `success: true, data: Customer[]`（数组）。
   - 建议：小程序客户选择器必须使用 `/customers/search`，参数用 `q`，并按数组处理。

3. **产品搜索返回结构假设错误（会导致选择器取不到列表）**
   - 小程序现有实现：产品列表走 `/products?search=...`，后端返回 `success: true, data: { data: Product[], pagination: ... }`（小程序 `product.service.ts` 已做适配）。
   - 文档示例：`response.items`。
   - 建议：订单模块复用 `productService.searchProducts()` 或完全照搬其“后端格式适配”逻辑，避免重复踩坑。

4. **费用项字段名/枚举与后端不一致（提交会直接 400）**
   - 后端校验：`feeType` 仅允许 `processing | shipping | other`；必须包含 `feeName`、`feeAmount`、`paidBy (customer|company)`。
   - 文档示例：`FeeType=SHIPPING/PROCESSING...`，字段用 `amount/payer`。
   - 建议：文档与实现统一为后端字段：`feeType/feeName/feeAmount/paidBy`，并将运费映射为 `feeType: 'shipping', feeName: '运费'`（或可配置）。

5. **“直接 confirmed”与后端库存预留规则冲突（会导致大量创建失败）**
   - 后端规则：普通销售 `status='confirmed'` 会执行库存预留并校验可用库存；且如果同一产品存在多个库存批次，未指定 `batchNumber` 会报错。
   - 文档当前表述：库存仅展示不强制限制、且不涉及批次选择。
   - 建议（必须二选一，且写入文档）：
     - 方案 A（推荐）：小程序先创建 `draft`，后续在 Web 端或小程序二期做“确认/发货”流程（确认时再校验库存/批次）。
     - 方案 B：保持直接 `confirmed`，则创建页必须支持：
       - 选择/输入 `batchNumber`（当产品存在多个批次时为必填）
       - 校验 `quantity <= availableQuantity`（否则提交必失败）

6. **“分享给客户”按钮的产品定义不清**
   - `open-type="share"` 分享的是小程序页面链接；外部客户通常没有系统账号/权限，点开会被要求登录或 401/403。
   - 建议：明确目标是“分享图片”而非“分享页面”：
     - 主路径：生成图片 → 保存到相册/长按转发（文档已写“长按图片可保存/分享”，这才是可行路径）
     - 可选：移除“分享给客户”按钮或改为引导文案（避免误解）

### P1：建议补齐，否则返工概率高

1. **权限方法示例与现有小程序 AuthService 不一致**
   - 现有方法是 `getCurrentUser()`；文档示例是 `getUserInfo()`。
   - 建议：文档统一按现有实现命名，避免照抄后编译失败。

2. **订单明细缺少关键字段规划**
   - 后端支持 `displayUnit/displayQuantity/piecesPerUnit`（“件/片”换算），并且库存预留按 `quantity(片)` 处理。
   - 建议：文档明确 UI 输入采用哪种单位，以及如何转换并提交 `quantity`（片），避免出现“用户填件数但后端按片数算”的错误。

3. **错误提示与失败分流策略不足**
   - 后端可能返回：库存不足、需要指定批次、客户不存在、权限不足等。
   - 建议：在文档补充“错误码/错误文案映射”和“用户下一步动作”（例如：提示选择批次/降低数量/重新登录）。

### P2：质量增强项（不阻塞，但建议规划）

1. **防重复提交（幂等性）**
   - 后端创建订单目前未使用 `withIdempotency`，用户连点会创建多单。
   - 建议：小程序提交按钮必须全程禁用；如需强保证，新增后端 idempotency 支持（Header 或 body）。

2. **Canvas 输出的适配与分页**
   - 文档固定 750×1000；当订单项 10+ 很可能溢出。
   - 建议：动态计算高度，或分多页渲染为多张图片（至少在文档里明确上限与降级策略）。

## 2. 与当前系统的“最小可行落地方案（MVP）”

为了保证 5 天工期可控，建议把 MVP 收敛为：

1. **创建订单：仅支持普通销售 + 草稿（draft）**
   - 原因：避开“库存预留 + 批次必填”带来的 P0 复杂度与失败率。
2. **客户选择：只做搜索选择器（/customers/search）**
   - 不做完整客户列表分页（避免响应格式差异与性能压力）。
3. **产品选择：复用现有 `productService.searchProducts()`**
   - 复用其对后端返回格式的适配与图片 token 追加逻辑（减少联调风险）。
4. **图片生成：以“长按保存/转发”为主路径**
   - 不承诺“分享页面给客户可用”。

若必须保持 `confirmed`（直接确认），则文档必须把“批次选择/库存校验”提升为 P0，并在 UI 里实现。

## 3. 建议补充到开发文档里的验收标准（AC）

### AC（接口契约）

- AC1：创建订单接口只依赖已存在路由（不再引用不存在的 `generate-order-number`），或明确新增后端路由的实现与权限。
- AC2：客户搜索使用 `GET /customers/search?q=...`，并能在小程序端正确渲染列表与选择。
- AC3：费用项字段与枚举满足后端校验（`feeType/feeName/feeAmount/paidBy`）。

### AC（业务规则）

- AC4（draft 路径）：创建 `draft` 订单成功率 99%+（在有权限、网络正常、客户/产品存在的前提下）。
- AC5（confirmed 路径，如选择）：当产品存在多个库存批次时，未选批次会提示并阻止提交；选批次后提交成功。

### AC（体验与稳定性）

- AC6：提交按钮防抖/禁用，连续点击不会重复创建订单。
- AC7：订单图片在 iOS/Android 主流机型生成成功；订单项超过阈值时有明确处理策略（分页/限制/滚动）。
