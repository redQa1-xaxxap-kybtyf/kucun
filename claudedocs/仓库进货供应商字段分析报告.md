useEffect(() => {
  const supplierIdValue = form.watch('supplierId');
  if (!supplierIdValue) return;

  items.forEach((item, index) => {
    if (!item?.supplierId) {
      form.setValue(`items.${index}.supplierId`, supplierIdValue, {
        shouldValidate: true,
      });
    }
  });
}, [form, supplierIdValue]);

### 3. 业务逻辑分析

#### 仓库进货流程
1. **手动入库**: 直接填写InboundRecord,不关联采购订单
   - ❌ 无法记录供应商信息
   - 只能通过remarks备注手动记录

2. **采购订单入库**: 通过采购订单创建入库记录
   - ✅ 通过purchaseOrderItemId关联到采购订单明细
   - ✅ 通过采购订单明细的supplierId间接获取供应商信息

#### 供应商追溯链路
```
InboundRecord (入库记录)
    ↓ purchaseOrderItemId
PurchaseOrderItem (采购明细)
    ↓ supplierId
Supplier (供应商)
```

## 🎯 问题分析

### 问题1: 数据模型冗余?
**答案**: ❌ **不存在冗余,目前InboundRecord中根本没有supplierId字段**

- PurchaseOrder的supplierId: 订单主供应商(用于快速筛选和显示)
- PurchaseOrderItem的supplierId: 明细实际供应商(核心业务字段,支持多供应商采购)
- InboundRecord: 没有supplierId,需要通过purchaseOrderItemId间接查询

### 问题2: 基本信息的supplierId是否必要?
**当前实现**: PurchaseOrder.supplierId是**必填字段**

**作用分析**:
1. ✅ **便捷性**: 用户体验好,选择主供应商后自动填充到明细
2. ✅ **查询优化**: 可通过订单supplierId快速筛选所有相关采购订单
3. ✅ **业务语义**: 反映采购订单的主要来源供应商
4. ⚠️ **潜在问题**: 当所有明细都来自不同供应商时,订单级supplierId变得语义不清

### 问题3: 基本信息的supplierId能否移除?
**技术可行性**: ✅ 可以移除
**业务影响**: ⚠️ 有重大影响

**如果移除,需要调整**:
1. 数据库Schema: 将PurchaseOrder.supplierId改为可选(nullable)
2. 前端表单: 移除订单级供应商选择器
3. 查询逻辑: 无法通过订单supplierId快速筛选
4. 显示逻辑: 订单列表需要显示"多供应商"或聚合明细供应商
5. 费用分摊: 运费等订单级费用难以归属到具体供应商

## 💡 建议方案

### 方案A: 保留订单级supplierId (推荐 ⭐)
**适用场景**: 大部分采购订单以单一供应商为主,偶尔混合采购

**调整建议**:
1. ✅ 保留PurchaseOrder.supplierId作为主供应商
2. ✅ 明确业务语义: "主要供应商"或"默认供应商"
3. ✅ 保持当前自动填充逻辑
4. ✅ 在订单显示时区分:
   - 单供应商: 显示供应商名称
   - 多供应商: 显示"主供应商(公司A) + 2个其他供应商"

**优点**:
- ✅ 用户体验好,减少重复输入
- ✅ 查询性能优,可用索引快速筛选
- ✅ 兼容现有业务流程

**缺点**:
- ⚠️ 多供应商场景语义略显模糊

### 方案B: 将supplierId改为可选
**适用场景**: 多供应商混合采购非常频繁

**调整方案**:
1. 修改Schema: `supplierId String? @map("supplier_id")`
2. 修改表单: 订单级供应商改为可选
3. 移除自动填充逻辑
4. 每个明细必须手动选择供应商

**优点**:
- ✅ 语义清晰,不会产生歧义
- ✅ 明确表达"每个明细独立选择供应商"

**缺点**:
- ❌ 用户体验下降,每个明细都要选供应商
- ❌ 查询效率降低,需要JOIN到明细表才能按供应商筛选
- ❌ 订单列表难以显示供应商信息

### 方案C: 完全移除订单级supplierId (不推荐 ❌)
**不推荐理由**:
- ❌ 失去订单维度的供应商快速检索能力
- ❌ 用户体验大幅下降
- ❌ 需要大量重构现有代码
- ❌ 运费等订单级费用难以处理

## 🔍 补充发现:InboundRecord缺少supplierId

### 当前问题
InboundRecord(仓库进货记录)没有supplierId字段,导致:

1. **手动入库无法记录供应商**
   - 用户手动入库时无法选择供应商
   - 只能在remarks备注中手动输入

2. **供应商追溯困难**
   - 需要通过purchaseOrderItemId → PurchaseOrderItem → supplierId
   - 两层JOIN才能获取供应商信息

3. **查询效率低**
   - 无法直接按供应商筛选入库记录
   - 影响供应商维度的成本和库存分析

### 建议:为InboundRecord添加supplierId

```prisma
model InboundRecord {
  id                   String   @id @default(uuid())
  // ... 现有字段
  supplierId           String?  @map("supplier_id") @db.Char(36)  // ⭐ 新增

  // 关系定义
  supplier             Supplier? @relation(fields: [supplierId], references: [id], onDelete: SetNull, onUpdate: Cascade)

  @@index([supplierId], map: "idx_inbound_records_supplier")  // ⭐ 新增索引
}
```

**好处**:
- ✅ 手动入库可以直接选择供应商
- ✅ 供应商追溯只需一次查询
- ✅ 支持供应商维度的成本分析
- ✅ 与采购订单入库保持一致(从明细自动填充)
